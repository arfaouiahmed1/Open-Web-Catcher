\chapter{Implementation}
\label{chap:implementation}

The implementation followed the project evolution described in Chapter~2. It
started from the company crawler baseline, used n8n to validate a browser-agent
fallback, and then formalized the maintainability direction through OWC. This
chapter describes what was implemented without claiming that the full
Python/FastAPI/Puppeteer platform replaced the existing company crawler.

\section{Existing Crawler Baseline}

\subsection{Company Puppeteer Crawlers}

The company already used Puppeteer-based browser automation to inspect known
streaming website patterns. Those crawlers could open targets, follow expected
paths, and collect useful evidence when the page structure matched previous
rules.

\subsection{What the Existing Crawlers Already Solved}

The baseline solved the operational need for repeatable collection on stable
patterns. It provided a practical starting point because the company already
understood browser automation, page traversal, and evidence handoff.

\subsection{Maintenance and Adaptation Limits}

The maintenance burden appeared when websites changed selectors, popups,
iframes, server controls, redirect paths, or stream-generation logic. A fixed
rule could fail even when a human reviewer could still recover the evidence by
observing the page and trying a different action.

\subsection{Why a Browser-Agent Layer Was Explored}

A browser-agent layer was explored to make the fallback path more adaptable and
traceable. The goal was not to remove crawler engineering, but to support it
when a known pattern stopped working and the page still contained recoverable
evidence.

\section{Prototype Phase with n8n}

\subsection{Prototype Goal}

The first objective was speed. n8n was used to validate whether an LLM-guided
browser workflow could classify streaming pages, navigate through landing and
hosting pages, activate players, and return useful evidence before investing in
a stricter architecture~\cite{n8n}.

\subsection{Why n8n Was Used}

n8n made it easy to connect browser actions, agent steps, intermediate outputs,
and manual inspection. That made it useful for experimentation even though it
was not the final architecture.

\subsection{n8n Landing Agent}

In the company context, the n8n landing agent was deployed as a backup solution
to support the existing crawler workflow. Its role was not to replace the full
crawler system. It provided a flexible fallback when crawler rules failed to
recover useful landing-page candidates after website changes.

\subsection{Validation on Real Websites}

The prototype was tested on real streaming pages with landing listings,
hosting pages, embedded players, popups, server switches, and delayed media
requests. These tests confirmed that a browser agent could recover evidence in
some cases, but also showed that long browser workflows need stronger state and
traceability.

\subsection{Relationship Between n8n and OWC}

n8n validated the browser-agent behavior and served as the backup deployment
artifact for the crawler workflow. OWC formalized the maintainable architecture:
clearer agents, stronger observability, typed persistence, richer evaluation,
and a more structured operator console.

\subsection{Implementation Areas}

Implementation work was divided across backend APIs, UI review surfaces,
browser tools, prompt contracts, persistence, provider/channel enrichment,
evaluation, and queue-driven deployment direction.

\section{Backend Implementation}

\subsection{FastAPI Run Control}

The backend starts investigations, resolves runtime settings, registers active
traces, and exposes APIs for workflow launch, single-agent tests, run detail,
configuration, pricing, provider lookup, and dataset execution.

Run control is implemented as the entry point of the evidence workflow. When a
URL is submitted, the backend creates the run record, attaches runtime
configuration, selects the agent route policy, and returns an identifier that
the console can use for progress and review. This boundary matters because the
browser-agent work can be slow: the UI should not own long-running browser
state, and the final run should remain inspectable even if the browser worker
fails later.

\subsection{Agent Execution}

Agent execution is organized around a route owned by the orchestrator. The
orchestrator prepares handoffs and calls specialists for classification,
landing discovery, hosting interaction, embedded-player inspection, and
downstream enrichment.

Each specialist receives a narrower task than the complete investigation. The
classification agent decides the page role; the landing agent searches for
hosting candidates; the hosting agent interacts with servers, popups, and
players; the embedded agent focuses on iframe/player-only contexts; and the
provider/email stage packages downstream context. The backend records the
input, output, status, and duration of each stage so that a failed run can be
debugged at the responsible boundary.

\subsection{Trace Assembly}

Run detail is assembled from multiple records: status, events, screenshots,
streams, tool calls, model usage, provider rows, channel context, and generated
drafts. This is why the backend acts as a review API, not only a job launcher.

The run-detail response is intentionally composite. A reviewer needs one screen
that answers several questions at once: what page was tested, which route was
selected, which browser actions were attempted, what the browser showed, which
stream evidence was found, how provider lookup behaved, and what the run cost.
The backend therefore assembles normalized persistence rows into a coherent
evidence bundle instead of returning only the final agent text.

\subsection{Configuration Access}

Runtime configuration includes model choices, pricing data, browser settings,
tool availability, provider keys, memory behavior, and dataset settings.

Configuration is read by the backend before a run starts and again by review
surfaces that explain model and pricing behavior. Keeping this access in the
backend avoids hardcoded frontend assumptions about available models, tool
profiles, provider keys, or pricing rows. It also makes it possible to compare
two runs by the settings that were active when they executed.

\subsection{Error Handling}

Errors are preserved as runtime events and stage outputs. The system favors a
clear failed or partial state over a confident answer without evidence.

This error policy is important for evidence work. A failed harvest, blocked
page, popup trap, missing provider contact, or timeout is still useful if it is
stored with the responsible stage and visible context. The implementation
therefore avoids hiding failures behind a generic completed status. It returns
partial or failed outcomes with enough trace data for an engineer or reviewer
to decide whether a rerun, prompt fix, tool fix, or manual review is needed.

\section{Operator Console Implementation}

\subsection{Run Launch Page}

The launch surface accepts target URLs or dataset batches and starts
traceable investigations.

The launch page is the operator's controlled entry point. It separates single
URL testing from dataset-backed batch execution, because these two modes serve
different needs. A single URL is useful for debugging a page family or a
regression case. A dataset batch is useful for comparing prompt, model, or tool
changes against previously working targets. Both modes create the same kind of
run records so their outputs remain comparable.

\subsection{Run Detail Page}

The run detail page shows status, stage outputs, screenshots, streams,
provider/channel context, tool history, model usage, and errors.

The detail page is designed around trace reconstruction. A reviewer should be
able to start from the final status and work backward to the classification
decision, specialist handoff, browser actions, screenshots, stream rows, and
provider enrichment. This view is where a run becomes reviewable: it connects
the final result to the concrete evidence and failure path.

\subsection{Evidence Review Page}

The evidence review view groups screenshots, media candidates, source pages,
provider rows, and reviewable email drafts so a human can decide whether the
run is usable.

This page avoids treating every successful technical extraction as operationally
accepted. The operator still checks whether screenshots support the claim,
whether stream or embedded evidence belongs to the investigated page, whether
provider context is useful, and whether an email draft is complete enough for
human approval. The system prepares the package, but it does not replace the
reviewer.

\subsection{Telemetry Dashboard}

The overview dashboard gives a compact operational snapshot: runs, strict
stream success, stream yield, total cost, total tokens, cached input, LLM
calls, tool success, recent events, active runs, and persistence health.

\subsection{Provider and Channel Review View}

Provider and channel views make downstream context explicit: detected channel
labels, stream hosts, provider names, countries, contacts when available, and
missing-data flags.

The implementation keeps channel detection, provider resolution, and abuse
contact discovery separate. A run may detect a broadcaster label but lack a
provider contact, or it may resolve a provider without a clear channel. Showing
these fields separately prevents the review interface from implying certainty
that the evidence does not support.

\subsection{Runtime Configuration View}

Runtime settings expose model selection, provider configuration, tool health,
and cost/pricing context for engineers.

This view supports maintenance. Engineers can check which model is active,
which provider catalog or pricing rows are available, which browser tools are
registered, and whether cost telemetry is being captured. That context matters
when an evaluation run changes behavior after a model, prompt, or runtime
configuration update.

\section{Browser Tool Implementation}

\subsection{Navigation Tool Implementation}

Navigation tools open targets, follow direct navigation, return to prior pages,
scroll to reveal content, and wait for page state. They return final URL,
readiness signals, and screenshots where relevant.

\subsection{Inspection Tool Profiles}

Inspection tools are split between lightweight context reads, targeted element
queries, frame/media detail, classification-oriented inspection, and
profile-specific landing/hosting/embedded inspection.

\subsection{Interaction Tool Implementation}

Interaction tools perform clicks, typing, selection, checkbox/radio actions,
media play attempts, gestures, coordinates, and the higher-level
\texttt{interact} flow. Interaction is followed by verification rather than
accepted as proof.

\subsection{Screenshot Capture}

Screenshots are captured for classification, player activation, evidence,
popup, blocker, and failure states. They are stored with the run so reviewers
can inspect the browser-visible claim.

\subsection{Stream and Manifest Harvesting}

\texttt{capture\_streams} and \texttt{harvest} capture \texttt{m3u8},
\texttt{mpd}, \texttt{mp4}, \texttt{webm}, iframe, DOM, player-object,
performance-entry, and network evidence after playback or player readiness is
observed.

\subsection{Popup, Tab, and Frame Handling}

The browser runtime records tab changes, closes unrelated popups when needed,
restores focus, and uses frame paths so tools operate on the intended page
context.

\subsection{Browser Profile-Scoped Sessions}

Profile-scoped sessions preserve state for a run while avoiding uncontrolled
sharing across unrelated investigations.

\subsection{Structured JSON Outputs}

Agent outputs are structured so the backend can persist them and the console
can render them consistently. Missing evidence is represented as an explicit
failure reason instead of omitted silently.

\subsection{Short Memory}

Memory is a hint layer. It can provide remembered selectors, pagination
patterns, navigation playbooks, server records, screenshots, stream URLs,
failure cues, and continuation notes, but the current browser state remains
the source of truth.

\subsection{Layout Hints}

Layout hints help agents avoid repeated broad inspection when a page family is
known. They are still validated against the live DOM and screenshot before use.

\subsection{Model Selection}

The selected model had to support long browser traces, reliable tool calls,
reasonable latency, and repeated regression runs at observable cost. Rate
limits, cached input, token usage, and pricing were therefore tracked during
evaluation~\cite{gemini-rate-limits,gemini-pricing,gemini-caching}.

\subsection{Token and Cost Tracking}

Each model call records model name, input tokens, cached input tokens, output
tokens, total tokens, and estimated spend when available.

\section{Persistence and Observability}

The persistence layer was implemented to answer two different review needs.
Evidence records support a human review decision: what was observed, what
stream or embedded-player evidence was collected, what screenshots support it,
which channel/provider context exists, and what draft was prepared. Telemetry
records support engineering diagnosis: which agent ran, which tool was called,
which model generated the decision, what failed, how long it took, and how much
it cost.

\input{figures/tikz/fig-05-persistence-review-flow}

\subsection{Stored Evidence Records}

Stored evidence records are the reviewable artifacts of the investigation.
They include screenshots, embedded URLs, stream or manifest candidates,
channel labels, provider rows, and generated email drafts. Each record keeps a
connection to the run and, where possible, to the page URL, frame context,
timestamp, and tool that produced it. This prevents the final evidence bundle
from becoming a loose list of URLs with no explanation.

The most important implementation choice is that evidence is stored even when
it is partial. A blocked screenshot, a failed player state, or a provider row
without an abuse contact can still explain why a run did not reach strict
success. For review, a traceable failure is better than a missing row.

\subsection{Stored Telemetry Records}

Telemetry records are the engineering record of the run. They include agent
runs, runtime events, model calls, tool calls, prompt compilations, errors,
and memory hints. These rows are not shown to the operator as raw logs only;
they are summarized into run detail, dashboard metrics, and regression views.

Separating telemetry from evidence keeps the review model clean. A reviewer
needs screenshots and stream context first, while an engineer needs event
order, tool status, model cost, and error detail. The same run therefore feeds
two interfaces: evidence review and system diagnosis.

\subsection{Runtime Event Logging}

Runtime events preserve the investigation timeline and make failed runs
diagnosable. Events are small and timestamped: run started, agent started,
tool requested, tool completed, screenshot captured, stream found, provider
resolved, failure recorded, and run completed. This timeline explains the
difference between superficially similar failures. For example,
\texttt{no\_streams} can mean that the player never activated, the harvest ran
too early, the browser was on a popup tab, or the target was blocked.

returns no stream, the tool-call order can show whether media readiness was

\subsection{Model Call Logging}

Model calls store prompt metadata, model selection, tokens, cached input, and
cost. During evaluation, this made it possible to compare prompt versions by
cost per useful run rather than by total spend alone. The implementation keeps
model provider, model name, prompt version, input tokens, cached input tokens,
output tokens, and estimated cost when those values are available. This is
also how the dashboard can explain why a regression run became more expensive
after a prompt or tool-policy change.

\subsection{Screenshot Storage}

Screenshots are stored as evidence and as debugging context for failures. The
implementation uses screenshots at meaningful state changes: classification,
landing candidate discovery, hosting activation, embedded-player inspection,
blocked pages, popup states, and final evidence or failure moments. The goal is
not to capture every wait loop; the goal is to preserve the visual state that
supports a claim or explains a failure.

\subsection{Error and Failure Recording}

Failures remain visible as structured status, stage, and reason fields. A run
can be \texttt{success}, \texttt{partial}, \texttt{failed},
\texttt{no\_streams}, \texttt{no\_hosting\_pages}, or \texttt{blocked}, but
the status alone is not enough. The implementation also stores the responsible
stage, visible blocker, last useful screenshot, last tool call, and error
message. This makes a failure actionable: the next fix can target the
classifier, landing discovery, hosting interaction, embedded harvest,
provider lookup, or runtime configuration.

\section{Provider, Channel Detection, and Email Preparation}

\subsection{Channel and Broadcaster Detection}

The workflow attempts to detect broadcaster/channel indicators from visible
page labels, DOM text, screenshots, stream context, and metadata. This keeps
the evidence model broader than a single rights holder while still supporting
the beIN SPORTS context when beIN indicators are detected.

\subsection{Stream Host Extraction}

Stream URLs and embedded-player URLs are normalized to hosts when possible so
provider enrichment can resolve infrastructure context.

\subsection{Provider Lookup}

Provider lookup uses host/IP and registration sources such as IP and RDAP data
to enrich stream evidence~\cite{ipinfo-api,icann-rdap}.

\subsection{Rights-Holder Email Context}

When channel context can be identified, the email stage can prepare a draft
using the corresponding rights-holder or contact context. When it cannot, the
missing channel context remains explicit.

\subsection{Reviewable Email Drafts}

Generated messages are drafts only. They group evidence, screenshots,
provider/channel context, and run identifiers for human review.

\subsection{Human Review Boundary}

The system does not send takedown emails automatically. A human reviewer
validates the evidence and decides downstream use.

\section{Deployment Direction}

\subsection{Company Crawler Environment}

The existing company crawler environment remains the operational baseline for
known patterns. The browser-agent work supports this environment instead of
claiming to replace it.

\subsection{n8n Landing Agent as Backup Solution}

The n8n landing agent was deployed as a backup to the existing crawler
workflow. When the crawler failed to recover useful landing-page candidates
after site changes, the n8n agent could inspect the page more flexibly and
return candidate URLs or evidence metadata for review or continuation.

\subsection{\texttt{agent\_tasks} Input Queue}

The deployment direction uses an Azure Service Bus input queue named
\texttt{agent\_tasks} for target URLs and task metadata.

\subsection{Browser Execution Container}

The browser execution container runs the workflow and Puppeteer tooling close
to the browser session so long investigations can run asynchronously.

\subsection{\texttt{agent\_results} Output Queue}

Results are returned through \texttt{agent\_results}: matched URLs, candidate
metadata, evidence references, and status. Queueing fits slow browser runs
because work can be retried and consumed asynchronously~\cite{azure-servicebus}.

\subsection{Relationship Between Backup Deployment and OWC}

The backup deployment is operationally useful for the crawler context. OWC is
the maintainable architecture that generalizes the approach with stricter
agents, richer observability, typed persistence, and repeatable evaluation.

\section{Implementation Summary}

The implementation moved from a known crawler baseline and n8n validation
toward a reviewable browser-agent architecture. The main engineering gain was
not a single extraction script. It was a runtime where prompt changes, browser
tools, screenshots, costs, stream evidence, channel/provider data, and failures
can be inspected together.
