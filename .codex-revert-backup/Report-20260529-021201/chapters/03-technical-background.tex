\chapter{Technical Background}

Before describing the architecture, this chapter defines the technical concepts
needed to understand browser-agent evidence collection. The goal is not to
describe every web technology in detail. It is to explain why dynamic streaming
pages require a rendered browser, interaction, media observation, screenshots,
and trace storage.

\section{Technical Nature of Streaming Evidence Collection}

\subsection{From Link Discovery to Reviewable Evidence}

Sports piracy monitoring is an evidence problem as much as a discovery problem.
Rights holders need to know what content was exposed, which page exposed it,
what technical indicators were visible, and whether the result can support a
later human review. A URL alone is weak if the system cannot explain how it was
reached.

\subsection{Evidence Collection Versus Content Download}

The system does not download protected content. It preserves reviewable
technical indicators: screenshots, visible page text, DOM signals, iframe URLs,
network requests, manifests, channel labels, provider metadata, and runtime
events. A manifest or media request is useful because it shows that a browser
path resolved toward playable media infrastructure, not because the system
stores the content itself.

\subsection{Why Dynamic Streaming Pages Are Difficult}

Illegal streaming pages often require JavaScript rendering, tab interaction,
server switching, popup recovery, iframe traversal, and timing-sensitive media
observation. A static HTTP response can miss the evidence because the useful
state appears only after a browser action.

\section{Structure of Illegal Streaming Websites}

\subsection{Landing Pages}

A landing page lists events, channels, schedules, leagues, or match cards. Its
main role is discovery: it points the workflow toward downstream hosting pages.

\subsection{Hosting Pages}

A hosting page contains the visible player shell, server controls, play
overlays, advertising traps, redirects, or iframe containers. Its main role is
activation: it must be interacted with before stream evidence may appear.

\subsection{Embedded Player Pages}

An embedded player page is a direct player or iframe URL. It may contain a
minimal UI but can expose the final media requests after play activation or a
short wait.

\subsection{Why Page Roles Matter}

Each page role requires different tools and stopping rules. A landing page
should discover candidates. A hosting page should activate and verify a player.
An embedded page should focus on player readiness and media harvesting.

\section{Browser-Rendered Pages and the DOM}

\subsection{Static HTML Versus Runtime DOM}

Modern streaming pages are not fully represented by their initial HTML. The
browser builds a Document Object Model (DOM), runs scripts, loads frames,
changes visible state after clicks, and emits network requests during playback
~\cite{whatwg-html}.

\subsection{DOM Signals Useful for Evidence Collection}

Useful DOM signals include links, buttons, server controls, iframe sources,
video elements, match cards, broadcaster labels, error messages, and popup
markers. These signals guide the next browser action and also explain why an
agent chose a route.

\subsection{Visual Evidence Versus Structural Evidence}

Structural evidence is not enough by itself. A screenshot can show whether the
player, channel label, blocker, popup, or error page was visible at the moment
the result was recorded. Visual evidence and DOM evidence therefore complement
each other.

\section{Media Streaming and Network Evidence}

\subsection{Adaptive Streaming Basics}

The most useful stream evidence is often a manifest or media request generated
after player activation. Adaptive streaming separates the playlist or
presentation description from the actual media segments.

\subsection{HTTP Live Streaming}

In HTTP Live Streaming (HLS), a player can load an \texttt{.m3u8} playlist that
points to media segments and quality levels~\cite{hls-rfc}.

\subsection{MPEG-DASH}

In MPEG-DASH, the player can load a media presentation description
(\texttt{.mpd}) that performs a similar role for adaptive playback
~\cite{dash-standard}.

\subsection{Progressive Media URLs}

Some players expose progressive media files such as \texttt{.mp4} or
\texttt{.webm}. These URLs are still evidence candidates when they appear in
the browser-visible path.

\subsection{Tokenized and Session-Bound URLs}

Some stream URLs include temporary tokens, signatures, or session-bound query
parameters. The system stores them as timestamped evidence artifacts with page,
frame, screenshot, and provider context instead of treating them as permanent
public links.

\section{Browser Automation and Runtime Instrumentation}

\subsection{Purpose of Browser Automation}

Browser automation controls a real browser session to inspect rendered pages,
click controls, manage frames, capture screenshots, and observe network
activity. This is why Puppeteer, Playwright, and Chrome DevTools Protocol are
relevant to this project~\cite{puppeteer,playwright,cdp}.

\subsection{Puppeteer and Browser Control}

Puppeteer can open URLs, execute clicks, read DOM state, inspect frames, and
attach to Chrome DevTools Protocol. In the project, this control is exposed
through bounded tools rather than unrestricted scripts.

\subsection{Network Observation}

Network observation captures media requests, response URLs, status codes, and
diagnostics. It is especially important when the page itself does not expose
the manifest in the visible DOM.

\subsection{Screenshot Capture}

Screenshots preserve what the browser showed during classification, player
activation, failure, or evidence capture. They are part of the evidence bundle
and the debugging trace.

\section{Runtime Obstacles in Streaming Websites}

\subsection{Popups and Advertising Overlays}

Popups can steal focus or open new tabs after a click. Advertising overlays can
hide the real player and make a successful tool call useless unless the agent
verifies the page state.

\subsection{Redirects and Mirror Chains}

Redirect chains can move the browser from a discovery URL to a mirror, an
advertisement, or a blocked page. Final URL and screenshot recording are
therefore required.

\subsection{Server Switching}

Many hosting pages provide several server buttons. The first server may fail,
so the agent must try alternatives deliberately and record which ones were
attempted.

\subsection{Iframe Complexity}

Players are often nested in iframes. The frame tree matters because media
requests may originate from the embedded context rather than the top-level
hosting page.

\subsection{Anti-Bot and Blocking Conditions}

Challenge pages, blocked requests, and bot checks can prevent playback. The
system should return a traceable blocked or failed state rather than inventing
evidence~\cite{cloudflare-challenges,ublock}.

\section{Agentic Workflows and Tool Use}

\subsection{Definition of an Agent in This Project}

An agent is a model-driven runtime component that receives a bounded task, uses
approved tools, observes the result, and returns structured evidence or a
failure reason. It is not an unrestricted crawler.

\subsection{Observe--Reason--Act--Verify Loop}

The core loop is to observe page state, decide the next action, act through a
browser tool, and verify that the page, frame, media, or screenshot state
changed in a useful way.

\subsection{Tool Contracts}

Tool contracts define what an agent can do and what evidence the tool returns.
The Model Context Protocol (MCP) provides a practical way to expose browser and
runtime tools through explicit inputs and outputs~\cite{mcp-spec}.

\subsection{Context, Memory, and Token Constraints}

Browser traces can become long. Memory hints can help choose selectors or
known layout patterns, but live browser evidence remains the source of truth.
Token and cache visibility matter because repeated evaluation batches can be
expensive~\cite{gemini-caching,gemini-pricing}.

\subsection{Why Specialist Agents Are Needed}

Specialist agents reduce drift. A landing agent discovers candidates, a hosting
agent activates players, and an embedded agent inspects player-only contexts.
This separation makes prompt behavior and failures easier to review.

\subsection{Runtime Traces}

A trace is the ordered record of runtime events, model calls, tool calls,
screenshots, status changes, stream candidates, provider rows, and failure
reasons. It explains how the result was reached.

\subsection{Human Review and Debugging}

Traceability supports both human review and engineering maintenance. A reviewer
can inspect the evidence bundle, while an engineer can identify whether a
failure came from classification, landing discovery, hosting interaction,
embedded-player inspection, provider lookup, or persistence.

\section{Chapter Summary}

Dynamic streaming evidence collection requires browser-rendered observation,
deliberate interaction, media and manifest capture, screenshots, and runtime
traces. These concepts lead directly to the architecture in the next chapter:
a staged browser-agent system with explicit tools, handoffs, persistence, and
human review boundaries.
