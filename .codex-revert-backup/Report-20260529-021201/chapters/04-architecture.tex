\chapter{System Architecture}
\label{chap:architecture}

The OWC architecture was designed around one constraint: every result must be
reviewable. A final stream URL is useful only if the system can explain how the
browser reached it, which agent made the decision, which tools were used, which
screenshot supports the claim, and where the workflow failed when no evidence
was found.

\section{Architectural Overview}

\subsection{Architecture Objective}

OWC formalizes the browser-agent approach into a modular reference
architecture. It is not presented as a microservices architecture and it does
not claim to replace the operational company crawler. Its objective is to make
evidence collection more adaptable, observable, and maintainable.

\subsection{Existing Crawler Problem and Architectural Response}

The existing Puppeteer crawlers were useful on known website patterns, but
required continuous updates when pages changed. OWC responds by separating
classification, landing discovery, hosting interaction, embedded-player
inspection, provider/channel enrichment, browser tools, and persistence. This
does not remove the need for maintenance, but it makes the failing boundary
clearer.

\subsection{Reviewability as the Main Design Constraint}

The architecture preserves evidence and decisions as normalized records:
runtime events, tool calls, model calls, screenshots, streams, embedded URLs,
provider rows, detected channel context, generated drafts, and final statuses.
When a run fails, the failure should be inspectable rather than hidden behind a
generic status.

\section{Use-Case View}

\subsection{Main Actors}

OWC has two main human roles. The operator launches investigations and reviews
evidence. The engineer maintains runtime settings, prompts, browser tools,
datasets, and evaluation behavior.

\subsection{Evidence Review Workflow}

The review workflow moves from run status to evidence bundle. The operator can
inspect screenshots, media candidates, channel/provider context, tool history,
model usage, and generated email drafts before deciding whether the result is
usable.

\section{Component Architecture}

OWC is split into the Next.js operator console, FastAPI backend, agent runtime,
MCP browser tool layer, PostgreSQL persistence, and external services. The
console does not own business logic or direct database access. FastAPI starts
jobs, resolves settings, assembles traces, and reads or writes normalized rows.
Browser interaction is handled through tools so the agent runtime remains
observable and bounded.

\input{figures/tikz/fig-component}

\subsection{Operator Console}

The console launches runs, follows live progress, exposes screenshots and
streams, shows provider/channel context, and lets engineers inspect settings,
pricing, datasets, and tool behavior.

\subsection{FastAPI Backend}

The backend owns run control, configuration access, active run state, API
responses, persistence writes, and trace assembly. It is the endpoint-driven
control layer for the platform.

\subsection{Agent Runtime}

The agent runtime executes the orchestrator and specialist agents. Each agent
receives a narrow task and returns structured output or a failure reason.

\subsection{Browser Tool Layer}

The browser tool layer exposes navigation, inspection, interaction, screenshot,
stream-capture, harvest, and memory tools. Tool calls are logged so their
inputs, outputs, status, and duration remain reviewable.

\subsection{Persistence Layer}

PostgreSQL stores run records, agent runs, runtime events, model calls, tool
calls, screenshots, streams, provider rows, email drafts, and final outputs.

\subsection{External Services}

External services include model providers, screenshot storage, provider/IP
lookup services, RDAP/WHOIS data, target websites, and queue infrastructure for
deployment direction.

\section{Browser Tool Architecture}

\subsection{Tool Layer Design Role}

The tool layer is the practical boundary between model reasoning and browser
state. Agents are not allowed to perform arbitrary browser automation. They
must call named tools, read structured results, and verify evidence after
state-changing actions.

\input{figures/tikz/fig-04-browser-tool-architecture}

\subsection{Navigation Tools}

Navigation tools move the browser to a target URL or page state. The exposed
tools are \texttt{open\_url}, \texttt{navigate}, \texttt{go\_back},
\texttt{scroll\_page}, \texttt{scroll\_to\_element}, and
\texttt{wait\_for\_page\_state}. \texttt{open\_url} includes challenge-page
detection and optional retry/wait handling. \texttt{navigate} reports final
URL, redirects or status, and a screenshot. \texttt{wait\_for\_page\_state}
supports network idle, navigation complete, selector or text presence, video
readiness, and challenge clearing.

\subsection{Inspection Tools}

Inspection tools observe rendered page state without changing it. The exposed
tools are \texttt{get\_page\_context}, \texttt{query\_elements},
\texttt{get\_element\_detail}, \texttt{get\_media\_state},
\texttt{get\_frame\_tree}, \texttt{inspect}, \texttt{inspect\_landing},
\texttt{inspect\_hosting}, and \texttt{inspect\_embedded}.
\texttt{get\_page\_context} is a lightweight compatibility read.
\texttt{query\_elements} returns targeted \texttt{element\_ref} handles.
\texttt{get\_element\_detail} reads localized detail around one DOM element or
subtree. \texttt{get\_frame\_tree} returns deterministic frame paths.
\texttt{get\_media\_state} focuses on playback readiness. The broad
\texttt{inspect} tool is classification-oriented, while
\texttt{inspect\_landing}, \texttt{inspect\_hosting}, and
\texttt{inspect\_embedded} are optimized for candidate discovery, player
activation, and nested player contexts.

\subsection{Interaction Tools}

Interaction tools deliberately change page state. The exposed tools are
\texttt{click\_element}, \texttt{click\_css}, \texttt{click\_text},
\texttt{click\_xpath}, \texttt{click\_checkbox}, \texttt{click\_radio},
\texttt{type\_into}, \texttt{select\_option}, \texttt{play\_media},
\texttt{swipe\_region}, \texttt{click\_coordinates}, and \texttt{interact}.
The \texttt{interact} tool supports modes such as click, play, type, select,
coordinates, check, checkbox, and radio, with locator strategies such as
\texttt{strict}, \texttt{xpath\_first}, \texttt{selector\_first}, and
\texttt{text\_first}. Interaction is not evidence by itself; it must be
followed by verification.

\subsection{Evidence Capture and Harvesting Tools}

Evidence tools preserve proof. The exposed tools are \texttt{screenshot},
\texttt{capture\_streams}, and \texttt{harvest}. \texttt{screenshot} supports
viewport, full-page, and element captures. \texttt{capture\_streams} is used
after playback starts and captures \texttt{m3u8}, \texttt{mpd}, and
\texttt{mp4} evidence from CDP, DOM, player objects, iframe sources, and
performance entries. \texttt{harvest} captures streaming URLs using six
detection layers and returns stream rows, protocol-split URL lists, screenshot
URL, network diagnostics, iframe diagnostics, and video state.

\subsection{Tool Modes and Output Depth}

The tool layer has several output depths. Lightweight context tools are used
for small compatibility reads. Targeted tools return narrow element or frame
detail. Broad inspect tools summarize a page after navigation or a meaningful
state change. Profile-specific inspect tools give landing, hosting, or
embedded agents compressed evidence for their task. Screenshot modes preserve
visual state, and harvest outputs preserve stream evidence and diagnostics.

\subsection{Tool Results as Traceable Runtime Events}

Every tool result contributes to the run trace. This matters for evaluation:
a tool can technically succeed while still being badly timed. The trace shows
whether the tool helped the evidence path.

\section{Agent Pipeline Architecture}

The pipeline is staged. The orchestrator receives the seed URL and controls the
run. It calls classification first, then routes to landing, hosting, or
embedded specialists. After stream evidence exists, provider/channel analysis
and email drafting can run. If no stream or embedded evidence exists, those
downstream stages are skipped.

\input{figures/tikz/fig-04-agent-pipeline-tools-evidence}

\subsection{Orchestrator}

The orchestrator initializes the run, calls classification, prepares handoffs,
aggregates outputs, decides final status, and records failure reasons.

\subsection{Classification Agent}

The classification agent identifies whether the current page is landing,
hosting, embedded, blocked, or other. It does not click, navigate through the
site, or harvest streams.

\subsection{Landing Page Agent}

The landing agent finds events, channels, match cards, candidate hosting URLs,
collapsed sections, and visible broadcaster hints.

\subsection{Hosting Page Agent}

The hosting agent activates players, handles popups, switches servers, finds
iframe or media candidates, and verifies state before harvesting.

\subsection{Embedded Page Agent}

The embedded agent focuses on player-only or iframe contexts, activates the
player when required, waits for media readiness, and harvests stream evidence.

\subsection{Provider and Channel Email Stage}

The provider and channel stage detects provider/channel context and prepares a
reviewable email draft. It does not browse websites and it does not send
emails automatically.

\subsection{Handoff Payload Structure}

A handoff includes target URL, page type, route source, evidence need, known
candidates, memory hints, navigation policy, tool budget, screenshot policy,
and failure-reporting rule. This prevents agents from inventing missing
context.

\subsection{Success and Failure States}

Common states are \texttt{success}, \texttt{partial}, \texttt{failed},
\texttt{no\_streams}, \texttt{no\_hosting\_\allowbreak pages}, and
\texttt{blocked}. The status must be tied to evidence or a clear failure
reason.

\subsection{Fail-Closed Routing}

If evidence is uncertain, the system should return a traceable failure rather
than hallucinated success. This rule is especially important when a page is
blocked, the stream is absent, or provider metadata is incomplete.

\section{Data and Evidence Persistence}

Persistence is part of the architecture, not a secondary storage detail. The
system produces reviewable evidence only when the final result can be connected
to the route, browser state, screenshots, stream candidates, tool calls, model
calls, provider lookups, and failure reasons that produced it. For this reason,
OWC stores evidence records and telemetry records separately but exposes them
together in the operator review flow.

\subsection{Run Records}

Run records are the root of the investigation. They store the submitted URL,
normalized URL, creation and completion timestamps, current status, final
status, route summary, evidence counts, cost totals, and final output summary.
The run record gives the operator a stable object to open, compare, rerun, and
cite during review. It also prevents evidence from becoming detached from the
target that originally produced it.

\subsection{Agent Run Records}

Agent run records describe what each specialist was asked to do and what it
returned. A classification record preserves page type, confidence, and route
reason. A landing record preserves candidate links and checked sections. A
hosting record preserves server attempts, popup handling, player state, and
embedded handoffs. An embedded record preserves player context and stream
harvest outcome. Provider and email records preserve enrichment status and
draft-generation state. This separation makes regression comparison practical:
an engineer can see which agent changed behavior between two runs.

\subsection{Runtime Events}

Runtime events preserve the investigation timeline. They answer the question
``what happened next?'' with small timestamped records: run started, agent
started, tool requested, tool completed, screenshot captured, stream found,
provider resolved, failure recorded, and run completed. When a run returns
\texttt{no\_streams}, the event timeline shows whether the agent never clicked
play, clicked the wrong control, lost focus to a popup, harvested too early, or
reached a blocked player.

\subsection{Tool Calls}

Tool call rows store tool name, input summary, output summary, status,
duration, active URL, and error detail. They are different from model calls:
the model explains an intended decision, while a tool row records an attempted
browser or provider operation. For browser-agent evaluation, call order is often
more important than call count. A successful \toolname{harvest} call before
player activation is still an implementation failure.

\subsection{Model Calls}

Model call rows store model provider, model name, prompt or agent version,
input tokens, cached input tokens, output tokens, estimated input cost,
estimated output cost, and total cost. These records make it possible to
compare prompt and model changes by useful evidence, not just by total token
volume. A cheaper run that fails important sites is not necessarily cheaper
operationally.

\subsection{Screenshots}

Screenshots preserve classification, evidence, playback, popup, blocked, and
failure states. They give reviewers a visual anchor for the final claim. A
useful screenshot should explain one moment: the landing candidates that were
visible, the hosting player before or after activation, the embedded player
state, a blocker page, or the final evidence state. Capturing every wait state
would create noise, so screenshots are tied to meaningful transitions.

\subsection{Stream Candidates}

Stream candidates store \texttt{m3u8}, \texttt{mpd}, \texttt{mp4},
\texttt{webm}, iframe, media, protocol, detection layer, source page, frame
context, timestamp, and screenshot reference where available. This matters for
tokenized media URLs: the URL can expire after the run, but the stored
timestamp, page context, and screenshot still explain where it was observed.

\subsection{Channel and Provider Records}

Channel/provider records store detected broadcaster context, hostnames, IP
information, provider names, countries, contacts when available, and missing
data flags. Provider lookup can partially succeed: a hostname and provider may
be identified even when no abuse contact is available. The architecture keeps
those states separate so the review output does not confuse missing contact
data with total enrichment failure.

\subsection{Evidence Bundle}

The evidence bundle groups status, screenshots, stream candidates,
channel/provider context, tool/model history, and reviewable email drafts for
operator inspection. It is not a new source of truth; it is a review grouping
assembled from the normalized records above. The bundle lets a human reviewer
accept the evidence, mark it partial, request a rerun, or reject it without
reconstructing the investigation from raw logs.

\section{Architecture Summary}

OWC is a controlled browser-agent architecture rather than one unrestricted AI
crawler. The operator starts a run, FastAPI controls execution and persistence,
the orchestrator routes work, specialists collect browser evidence, the tool
layer records observable actions, and normalized records preserve successful
outputs and failure paths. The next chapter explains how this design was
implemented from the crawler baseline and n8n validation workflow.
