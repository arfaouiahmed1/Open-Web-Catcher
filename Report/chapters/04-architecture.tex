\section{Architectural layers}

\subsection{Execution and API layer}

The FastAPI backend is the entry point for runs, status checks, traces, and evaluation
routes. It isolates runtime control from browser internals and gives the operator
console a stable interface. Key endpoints include:

\begin{itemize}
  \item \texttt{POST /runs} — submit a seed URL and start an investigation run;
  \item \texttt{GET /runs/\{id\}/events} — stream live run events;
  \item \texttt{GET /runs/\{id\}/artifacts} — retrieve stream evidence and screenshots;
  \item \texttt{GET /evaluate} — access the evaluation and review surface.
\end{itemize}

\subsection{Agent orchestration layer}

The orchestrator coordinates execution order and specialist handoff. It is intentionally
lightweight so routing logic stays understandable and model-intensive work stays in
specialist agents. The orchestrator calls the classification agent first on every URL,
then dispatches to the appropriate specialist based on the classification result.

\subsection{Specialist-agent layer}

The specialist layer contains four focused roles. Each agent has its own system prompt,
tool set, and stopping criteria. This structure reduces over-general prompts and makes
failure analysis more precise. Agent composition is detailed in
Chapter~\ref{chap:implementation}.

\subsection{Browser tool layer}

The browser tool layer exposes controlled actions (inspect, navigate, click, screenshot,
harvest). It acts as the boundary between model decisions and browser-side execution.
All tools are implemented as Node.js Puppeteer processes invoked from the Python backend.

\subsection{Anti-evasion and runtime-hygiene layer}

A dedicated anti-evasion perspective is required in this domain. The architecture embeds
runtime hygiene policies that were validated during the internship:

\begin{itemize}
  \item realistic browsing behavior and pacing;
  \item fingerprint profile hardening and periodic adjustments;
  \item adaptive adblock behavior rather than static one-time setup;
  \item interaction fallbacks for overlays and unstable selectors;
  \item evidence-first operation (screenshots + network + DOM state).
\end{itemize}

\subsection{Persistence, memory, and observability layer}

This layer stores runs, events, tool calls, LLM calls, and output artifacts. It enables
post-mortem analysis and supports both short-term and long-term memory strategies.

\subsection{Operator interface layer}

The Next.js operator console provides run launch, live tracing, historical inspection,
and evaluation navigation. It is designed for operational review, not only developer
debugging.

\section{Memory and knowledge reuse architecture}

\subsection{Run-level (short-term) memory}

Run-level memory captures local progress for the active session: visited pages, tried
actions, discovered signals. It reduces repeated failures in the same run by making
previous tool call results available to the agent in the same conversation context.

\subsection{Cross-run (long-term) memory}

Cross-run memory stores reusable site knowledge between runs. It supports faster warm
starts on recurring domains by reusing successful selectors, layout patterns, and
server strategies. The memory is implemented as a structured database keyed by domain
and page-type.

\section{Caching and cost-aware architecture}

Cost control is part of the architecture, not an afterthought. The main mechanisms are:

\begin{itemize}
  \item provider-aware prompt caching (LLM system prompts cached across turns);
  \item tool-result reuse when observations are identical within a run;
  \item specialist routing to avoid unnecessary heavy steps on simple cases;
  \item per-run cost visibility in observability surfaces.
\end{itemize}

\textbf{Important implementation note.} During the internship execution phase, Azure
Service Bus and Azure Container Apps Jobs were \textbf{documented as target architecture}
but were \textbf{not used in daily runtime}. Most runs were executed in
local/containerized environments while preserving cloud-compatible design boundaries.

The n8n prototype confirmed feasibility but had structural limits at scale: workflow context was local to each execution, large flows were hard to debug, and prompt/tool evolution was difficult to govern. The coded platform addresses all three: an explicit Python orchestrator with versioned prompts, persistent memory, and per-event structured traces. That transition is what makes long-term operation feasible as a maintainable evidence collection system.
