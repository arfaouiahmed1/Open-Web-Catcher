\chapter{System Architecture}
\label{chap:architecture}

This chapter describes the system at architecture level before Chapter~5
discusses implementation details. The objective is to keep the overview readable:
diagrams show the main structure and tables carry the detailed responsibilities.
This avoids diagrams that try to encode every internal connection and become
hard to read.

The architecture is presented through four views: use cases, logical run flow,
code/data structure, and physical runtime. Together, these views explain how an
operator starts an investigation, how agents cooperate, which services support
the workflow, and where the main runtime components are located.

\section{System Overview and Use Cases}

The platform is an evidence-collection workbench for illegal streaming websites.
The main actor is the operator, who launches runs and reviews evidence. The
engineer or administrator maintains prompts, models, datasets, browser runtime
settings, and tool configuration. External services provide LLM inference,
target website content, screenshot storage, and provider ownership data.

\section{Logical Agent Architecture}

The logical workflow is intentionally staged. Classification decides the page
type, the orchestrator routes work to the correct specialist, and extracted
evidence is enriched before review. The most important routing rule is that
landing, hosting, and embedded pages are different page types, so they require
different browser strategies.

\subsection{Validation and Repair Loop}

Browser automation cannot be a static scrape in this domain. Popups, ad tabs,
cookie banners, Cloudflare-style interstitials, unstable selectors, and nested
iframes can change the state after each click. The runtime therefore uses a
simple observe-act-validate loop.

\section{Memory and Caching Summary}

Memory and caching are support mechanisms, not separate product features. They
exist to reduce repeated work, preserve useful domain knowledge, and make cost
visible.

\section{Chapter Summary}

This chapter defined the system at architecture level. The key idea is a staged,
reviewable evidence-collection pipeline: the operator starts and reviews runs,
the API controls execution, the orchestrator routes across page-type specialists,
MCP browser tools gather evidence, and storage preserves the result for later
inspection. Chapter~5 now moves from this architecture to the concrete
implementation.
