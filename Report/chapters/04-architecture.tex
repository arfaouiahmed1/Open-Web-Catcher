\chapter{System Architecture}
\label{chap:architecture}

This chapter presents the reference architecture of the evidence-collection
platform before Chapter~5 moves into implementation details. The goal is to
show the system through a small set of complementary views: who uses it, which
runtime components cooperate, how the agent route is controlled, what a normal
run sequence looks like, and which data structures make the result reviewable.

\section{System Purpose and Actors}

The platform is an evidence-collection workbench for illegal streaming
websites. The operator launches investigations and reviews the resulting
evidence. The engineer or administrator maintains models, prompts, pricing,
datasets, browser runtime settings, and MCP tool configuration. External
services provide target website content, model inference, screenshot storage,
and provider ownership data.

\section{Runtime Component Architecture}

The runtime separates the operator console, API, agent execution, browser
automation, persistence, and external enrichment services. The Next.js console
does not access the database directly; it calls FastAPI endpoints. FastAPI owns
background-job execution, active trace assembly, settings resolution, and
database access. Browser work is delegated to profile-scoped MCP tooling so the
agents receive only the tools allowed for their page type.

\input{figures/tikz/fig-component}

This separation is practical rather than cosmetic. LLM reasoning, browser
automation, persistence, and dashboard rendering fail in different ways, so the
architecture keeps their boundaries visible. Runtime memory, prompt caching,
tool-result caching, and validation/repair behavior support the agent loop, but
they are not separate product flows in this chapter; Chapter~5 describes those
implementation mechanisms.

\section{Logical Workflow and Agent Routing}

The orchestrator is the routing authority. It checks memory as soft guidance,
calls classification, prepares handoffs, executes landing, hosting, and
embedded specialists as needed, aggregates structured outputs, then runs
provider analysis and email generation only when stream evidence exists. This
keeps failures interpretable: a classification timeout, missing hosting
candidate, hosting-player failure, embedded-player failure, and provider skip
are different operational states.

\section{Chapter Summary}

The architecture is a staged, reviewable evidence pipeline. The operator starts
and reviews runs through the console. FastAPI controls execution and persistence.
The orchestrator routes across page-type specialists, MCP browser tools gather
page and network evidence, provider and email tools run only after streams
exist, and storage preserves both the final answer and the failure path. The
next chapter maps these architecture boundaries to the concrete implementation.
