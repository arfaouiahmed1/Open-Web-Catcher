\chapter{Technical Background and Working Tools}

This chapter establishes the technical context required to understand the design choices
made in subsequent chapters. It covers the structural challenges of illegal streaming
websites, the core technologies selected to address them, the streaming protocols that
the platform is designed to capture, and the residual limitations that motivate an
adaptive agentic approach rather than a fixed scraper.

\section{Why this domain is hard in practice}

Illegal streaming websites are difficult to automate because they are built for volatility. In a single run, the same domain can present list pages, server switchers, nested player frames, popups, redirects, and anti-bot interstitials. A system that succeeds only on static HTML snapshots will fail frequently in this environment.

From repeated runs, the main difficulties were:

\begin{itemize}
  \item content that appears only after user-like interaction;
  \item deeply nested iframe trees where the useful player is not in the top frame;
  \item unstable selectors caused by obfuscation and frequent layout changes;
  \item anti-bot behaviors that escalate after repetitive scripted actions;
  \item stream URLs that are signed, short-lived, or generated after runtime JavaScript logic.
\end{itemize}

\section{From deterministic scripts to adaptive agents}

The core difficulty in this domain is that no fixed rule generalizes across all page
structures. A deterministic scraper works well on stable pages with known selectors, but
fails when controls appear only after interaction, when the useful player is buried in an
iframe chain, or when the site changes behavior between sessions. For this reason, the
project moved toward an adaptive browser-assisted approach in which the system observes the
current page state, chooses the next action, and re-evaluates the result before proceeding.
Research on agentic reasoning and realistic web benchmarks such as WebArena supports this
kind of iterative decision-making on dynamic interfaces~\cite{agent-survey,webarena}.

\section{ReAct as the operating pattern}

In practice, the specialist agents follow a ReAct-style loop~\cite{react}: observe the
current browser state, reason about the next step, act through a browser tool, and check
whether the action produced useful evidence. This operating pattern is better suited to
streaming sites than a linear workflow because it can recover from false clicks, inactive
server buttons, popup interruptions, and empty first attempts.

The practical advantages for this project are straightforward:
\begin{itemize}
  \item the next action depends on the actual page state, not on a fixed branch decided in advance;
  \item every important step can be validated through DOM, screenshot, or network evidence;
  \item the run can stop early when evidence is found, or fall back when the current path fails.
\end{itemize}

\section{Observed website families in practice}

During manual and semi-automated campaigns, a broad range of streaming-site structures
were encountered. They can be organized into two main axes: \emph{simple/static sites}
(those with predictable HTML and stable selectors) and \emph{complex/interactive sites}
(those requiring JavaScript navigation and dynamic interaction to reveal content).

\subsection{Simple sites: WordPress-template regional aggregators}

A large percentage of regional Arabic-language football streaming portals are built
on the same WordPress theme family. Several sites in this category were observed to
share identical CSS class names, the same component hierarchy, and even the same
player plugin (AlbaPlayer or Clappr embedded via a shortcode). This made them the
easiest target family: once a selector pattern was confirmed on one site, it often
transferred directly to another within the same template cluster.

Operational traits:
\begin{itemize}
  \item match pages from repeating templates where visible layout is stable;
  \item server buttons with predictable class names (\texttt{.server-btn},
    \texttt{.stream-link}) that can be targeted by selector;
  \item ad and redirect logic injected by plugins or external \texttt{<script>} tags;
  \item occasional template refresh that preserves URL structure but updates class names.
\end{itemize}

These sites are called ``simple'' because a well-formed selector-based interact call
succeeds on the first attempt in the majority of runs.

\subsection{Complex sites: JavaScript-heavy interactive portals}

Complex sites require navigational interaction before useful content becomes visible.
Common patterns include:

\begin{itemize}
  \item \textbf{Tab-gated match listings:} the landing page shows only live matches by
    default; other events are behind tab controls that trigger JavaScript fetches
    (no page reload) when clicked;
  \item \textbf{Dynamic server loading:} server options are not in the initial HTML but
    are injected by an XHR response triggered by selecting a server tab;
  \item \textbf{Scroll-gated content:} match cards below the fold are lazy-loaded and
    only appear after a scroll event reaches a threshold;
  \item \textbf{Login-wall or subscription interstitials:} some mirrors show a blurred
    player until a fake login form is dismissed.
\end{itemize}

These sites require the landing or hosting agent to perform a multi-step navigation
loop (inspect $\to$ interact $\to$ re-inspect) before extraction can begin.

\subsection{Global link-hub aggregators}

Global indexes (such as streamed-style hubs) frequently act as routing layers rather
than final player pages. They are neither purely Arabic nor purely WordPress; their
structure is custom but their routing behavior is consistent:

\begin{itemize}
  \item large event listings with many outbound host domains;
  \item per-event pages that aggregate multiple mirrors with inconsistent UI patterns;
  \item rapid provider rotation where one mirror fails while another becomes active;
  \item mixed language/region metadata that complicates deterministic field extraction.
\end{itemize}

\section{Why returning only HTML does not work}

For this project, plain HTML retrieval is insufficient for five concrete reasons:

\begin{enumerate}
  \item many pages render critical controls through JavaScript after load;
  \item active stream URLs often appear only in network requests after play/click actions;
  \item iframe content can be isolated and absent from the top-level DOM snapshot;
  \item anti-bot defenses may show alternate HTML to suspicious sessions;
  \item visible state transitions (loading, paused, playing, error overlays) require
    visual confirmation.
\end{enumerate}

This is why browser-assisted extraction is not optional in this domain.

\section{Page taxonomy with examples, inputs, and outputs}

The system works on four page types.

\subsection{\texttt{landing\_page}}

Role: discover candidate hosting pages and match-level context.

Typical signals: match cards or rows, team name pairs, date/time tabs, score indicators,
links containing ``matches'', ``live'', or ``events'' path segments.

Expected outputs: ranked list of hosting-page URLs, extracted match metadata (teams,
leagues, broadcasters), navigation evidence (screenshots, link structure).

\subsection{\texttt{host\_page}}

Role: activate servers/players and extract stream evidence from hosting context.

Typical signals: single-match focus, server-switch buttons (serv1/serv2/serv3 labels),
a visible player container, embedded iframe with albaplayer/clappr/hls.js, beIN Sports
logo watermark.

Expected outputs: stream manifests (m3u8/mpd), per-server evidence, iframe embed URL
for fallback, screenshots confirming active play state.

\subsection{\texttt{embed\_video\_page}}

Role: extract streams from iframe-centered player pages and fallback contexts.

Typical signals: minimal page with single player occupying most of the viewport, no
navigation or ads, play button in center, network requests include \texttt{.ts} segments.

Expected outputs: final stream manifests after play activation, player-state diagnostics,
iframe content diagnostics.

\subsection{\texttt{other}}

Role: filter noise pages (ads, unrelated redirects, irrelevant content) to protect
runtime budget.

\section{From the n8n phase to the new Python project}

The company initially requested an n8n-based phase to validate feasibility quickly on
real targets. That phase successfully confirmed the concept, but it also exposed
limitations that became critical at scale:

\begin{itemize}
  \item memory was mostly local to one workflow execution;
  \item long end-to-end flows were hard to keep stable when many hosting pages/servers
    were involved;
  \item parallel branches increased operational complexity and recovery difficulty;
  \item large workflows became difficult to maintain and reason about as prompts/tools
    evolved.
\end{itemize}

This is why the work moved to the new Python-based implementation with explicit memory,
stronger observability, better runtime control, and clearer engineering boundaries.

\section{Difficulties faced and what was done}

\subsection{Nested iframes and frame ambiguity}

\textbf{Difficulty.} Useful players were often hidden several levels deep, and top-level
signals were misleading.

\textbf{Handling.} Frame-tree inspection plus iframe diagnostics, combined with targeted
interactions and post-action re-inspection.

\subsection{Popups, overlays, and click traps}

\textbf{Difficulty.} Blocking overlays interrupted server switching and fake controls
diverted the run.

\textbf{Handling.} Fallback click strategy with text matching, visibility checks,
scroll-and-click, and JavaScript click as final fallback.

\subsection{Tokenized and hidden stream paths}

\textbf{Difficulty.} Some pages did not expose a direct \texttt{m3u8} in initial HTML;
stream access was generated after runtime token exchange.

\textbf{Handling.} Stream extraction was moved to runtime evidence layers: CDP
request/response monitoring, player API inspection, performance resource scans, and
post-activation harvesting.

\subsection{Anti-bot pressure}

\textbf{Difficulty.} Repetitive automation patterns triggered challenges and degraded
extraction continuity.

\textbf{Handling.} Normal-user behavioral pacing, reduced automation signals, adaptive
retries, and evidence-first fallback when full extraction was blocked.

\section{How target websites intentionally break extraction}

Across both site families, the following break tactics were observed repeatedly:

\begin{itemize}
  \item multi-step redirect chains designed to open popups before revealing the real
    player;
  \item nested iframe delegation across different domains to hide where the final media
    request originates;
  \item short-lived signed stream URLs (token + expiry) generated only after user-like
    interaction;
  \item bait resources and noisy assets that look important but are unrelated to the
    playable stream;
  \item anti-bot challenge pages that change response content when automation signals
    are detected.
\end{itemize}

\section{Screenshot storage: Cloudinary CDN}

Each agent calls \texttt{screenshot()} after key state transitions. The resulting
images serve as primary evidence: they confirm player activation, show server labels,
and provide human-auditable context for any extracted stream URL.

Screenshots are stored using the \textbf{Cloudinary} media CDN. After Puppeteer
captures a PNG buffer, the tool uploads it to Cloudinary via their Upload API and
receives back a persistent URL. This URL is stored alongside the run event in
PostgreSQL and displayed in the operator console.

\textbf{Why Cloudinary rather than local storage?}
\begin{itemize}
  \item screenshots are immediately accessible from the operator console without
    needing to serve files from the backend;
  \item Cloudinary applies automatic compression and resizing via URL parameters,
    keeping evidence lightweight without losing diagnostic quality;
  \item the CDN URL is stable and can be embedded in takedown emails as external
    evidence links;
  \item it decouples screenshot storage from the backend container, simplifying
    cloud deployment where ephemeral container storage would otherwise lose evidence.
\end{itemize}

\section{Ad blocking with uBlock Origin}

Illegal streaming sites monetize through aggressive advertising. This creates two
problems for automated extraction:

\begin{enumerate}
  \item popups and interstitial ads occupy new browser contexts and divert the agent's
    interaction away from the real player controls;
  \item redirect chains triggered by ad click events can leave the original page
    in an unusable state.
\end{enumerate}

The browser profile uses \texttt{uBlock Origin} as the main preventive layer, while the
agents keep explicit popup-recovery behavior for cases where extension-level filtering is
not sufficient.

\subsection{uBlock Origin}

uBlock Origin operates as a Chromium extension loaded at browser launch. It intercepts
network requests at the extension level, blocking ad server domains, tracking pixels,
and ad-injecting scripts before they execute. This prevents the majority of popup-opening
ad scripts from running at all.

Configuration points tuned during the internship:
\begin{itemize}
  \item filter list selection: EasyList + EasyPrivacy as the baseline, supplemented by
    regional filter lists relevant to Arabic streaming domains;
  \item dynamic filtering: specific CDN domains used for player content were
    \emph{whitelisted} to prevent false positives that blocked player assets;
  \item the extension was loaded via \texttt{--load-extension} and
    \texttt{--disable-extensions-except} Puppeteer flags to avoid fingerprint signals.
\end{itemize}

\textbf{Limitation of extension filtering.} No extension is a complete solution. Sites
that serve ad content from the same domain as player content cannot be filtered without
breaking the player. This is why the hosting and embedded agents retain explicit popup
handling logic (detect new tab $\to$ close $\to$ retry) as a fallback even when
ad-blocking is active.

\section{Streaming protocol infrastructure}

Understanding the protocols used by streaming piracy infrastructure is a prerequisite for
understanding what the platform is designed to capture. Piracy hosts do not use a single
streaming technology: content is served over several adaptive-bitrate protocols, each with
its own manifest format, URL structure, and tokenization scheme. The \texttt{harvest} tool
is built to intercept all of them simultaneously.

\subsection{HLS — HTTP Live Streaming}

HLS~\cite{hls-rfc} is the dominant adaptive-bitrate protocol encountered in this domain.
It is text-based and organized in a strict two-level hierarchy.

The \textbf{master playlist} (commonly named \texttt{index.m3u8}, \texttt{manifest.m3u8},
or \texttt{playlist.m3u8} depending on the CDN) lists every available rendition with its
bitrate, resolution, and codec. Each rendition entry points to a \textbf{variant playlist}
that contains time-coded references to the actual MPEG-2 Transport Stream media segments
(\texttt{.ts} files). The player selects the appropriate variant based on available
bandwidth.

From an evidence perspective, the master playlist URL is the most important artifact because
it is the entry point that ties the stream to a specific CDN path. Several URL patterns
appear regularly across piracy infrastructure:

\begin{itemize}
  \item \texttt{/live/index.m3u8} — the canonical HLS master playlist;
  \item \texttt{/stream/mono.m3u8} — a single-rendition playlist that skips the master
    level; the player goes directly to segments;
  \item \texttt{/hls/playlist.m3u8?token=\textit{xxx}\&expires=\textit{timestamp}} —
    a tokenized manifest where signed query parameters grant short-lived CDN access;
  \item \texttt{/live/manifest.m3u8} — an alternative naming convention common on
    infrastructure built around open-source re-streaming panels.
\end{itemize}

Tokenized manifests are the most operationally significant variant. The token in the query
string is signed by the CDN key server and carries an expiry timestamp. The \texttt{harvest}
tool captures the full URL including the token at the moment the browser requests it,
preserving complete evidence before the token expires.

\subsection{MPEG-DASH}

MPEG-DASH (Dynamic Adaptive Streaming over HTTP, ISO/IEC 23009-1) is the second protocol
regularly encountered. Unlike HLS, DASH manifests are XML documents (\texttt{.mpd}) that
describe a hierarchical segment addressing scheme:

\begin{itemize}
  \item \textbf{MPD} (Media Presentation Description) — the root XML manifest;
  \item \textbf{Period} — a contiguous time range of the presentation;
  \item \textbf{AdaptationSet} — a group of representations sharing the same media type
    (video, audio, or subtitles);
  \item \textbf{Representation} — one specific quality level with its codec and bitrate;
  \item \textbf{SegmentTemplate} or \textbf{SegmentList} — the addressing scheme for
    individual \texttt{.m4s} fragment files.
\end{itemize}

The \texttt{harvest} tool captures DASH manifests via the URL pattern
\texttt{/\textbackslash.mpd(\textbackslash?|\$)/i}, which matches naming conventions such
as \texttt{manifest.mpd}, \texttt{stream.mpd}, and \texttt{dash.mpd}.

\subsection{Additional protocols captured}

Beyond HLS and DASH, the \texttt{harvest} tool captures three further protocol families:

\begin{itemize}
  \item \textbf{Progressive MP4} (\texttt{.mp4}) — static download links embedded in
    player configuration objects; less common on live streams but present on replay and
    clip pages.
  \item \textbf{WebM} (\texttt{.webm}) — the Chromium-native open container format, used
    on some alternative-player implementations and lower-quality fallback streams.
  \item \textbf{Smooth Streaming} (\texttt{.ism/manifest}) — the Microsoft-origin
    fragmented-MP4 format, occasionally found on infrastructure using legacy streaming
    servers.
\end{itemize}

\subsection{The harvest tool's six-layer capture strategy}

The \texttt{harvest} tool uses six parallel detection layers to ensure manifest URLs are
captured regardless of which protocol is in use and regardless of whether the manifest
loaded before the tool was invoked:

\begin{enumerate}
  \item \textbf{CDP \texttt{Network.requestWillBeSent}} — the Chrome DevTools Protocol
    fires this event for every outgoing network request, including from within cross-origin
    iframes. This is the primary layer and fires before the request leaves the browser.
  \item \textbf{Puppeteer response listener} — a secondary \texttt{page.on('response')}
    handler provides redundancy and captures response HTTP status codes alongside the URL.
  \item \textbf{DOM element scan} — the tool queries \texttt{<video src>} and
    \texttt{<source src>} attributes for statically embedded stream references.
  \item \textbf{JavaScript player API inspection} — \texttt{page.evaluate()} probes
    known player surfaces: hls.js instance URLs, video.js current source, jwplayer
    playlist items, and dash.js manifest references.
  \item \textbf{\texttt{performance.getEntriesByType('resource')}} — a retroactive
    resource-timing scan recovers manifest URLs loaded before the tool began listening.
  \item \textbf{Frame-level CDP session} — when the player is in a cross-origin iframe,
    a dedicated CDP session is opened on that frame to capture its network traffic
    independently.
\end{enumerate}

All captured URLs are matched against the protocol patterns and returned grouped by
protocol. The concrete implementation is detailed in Chapter~5.

\section{Remaining limitations of rule-based approaches}

Even with the mitigations above, difficult websites remain. This justifies the fallback
role of the agentic path:

\begin{itemize}
  \item some protections still force partial evidence outcomes;
  \item highly dynamic pages can invalidate previously successful selectors quickly;
  \item operational cost grows with deeper exploration and server count.
\end{itemize}

For this reason, the adaptive workflow is used where its flexibility provides clear
recovery value.

With the technical background established — the domain challenges, the tools selected to
address them, the streaming protocols being targeted, and the remaining limitations that
motivate adaptivity — Chapter~3 formalizes the methodology, requirements, and design
constraints that guided the system's architecture.
