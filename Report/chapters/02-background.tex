\chapter{Technical Background and Working Tools}

This chapter establishes the technical context required to understand the design choices
made in subsequent chapters. It covers the structural challenges of illegal streaming
websites, the core technologies selected to address them, the streaming protocols that
the platform is designed to capture, and the residual limitations that motivate an
adaptive agentic approach rather than a fixed scraper.

\section{Why this domain is hard in practice}

Illegal streaming websites are difficult to automate because they are built for volatility. In a single run, the same domain can present list pages, server switchers, nested player frames, popups, redirects, and anti-bot interstitials. A system that succeeds only on static HTML snapshots will fail frequently in this environment.

From repeated runs, the main difficulties were:

\begin{itemize}
  \item content that appears only after user-like interaction;
  \item deeply nested iframe trees where the useful player is not in the top frame;
  \item unstable selectors caused by obfuscation and frequent layout changes;
  \item anti-bot behaviors that escalate after repetitive scripted actions;
  \item stream URLs that are signed, short-lived, or generated after runtime JavaScript logic.
\end{itemize}

\section{From deterministic scripts to adaptive agents}

The fundamental challenge is that no single rule generalizes across all the page structures
encountered. A static scraper excels on predictable pages with stable selectors, but breaks
when layout or anti-bot behavior changes. The solution is an adaptive system that can
\emph{observe}, \emph{reason}, and \emph{act} iteratively, adjusting strategy based on
what it actually finds on the page. Large language model based autonomous agents have been shown to handle precisely this
kind of open-ended, multi-step decision-making in environments where the state space is
too large to enumerate in advance~\cite{agent-survey}. Benchmark environments such as
WebArena~\cite{webarena} have demonstrated that LLM-driven agents can navigate realistic
web interfaces, execute multi-step tasks, and generalize across different website
structures without site-specific hand-coding.

ReAct works well here because each observation is a fresh browser state — new HTML, new screenshot, updated network events captured after the last action. The agent doesn't reason from a snapshot taken at page load; it reasons from what the page looks like right now. That means it can notice when a server click opened an ad popup instead of activating the player, or when the player is still showing an idle state after what looked like a successful play click. The loop gives the agent a chance to recover rather than committing to an incorrect first read.

\section{Why returning only HTML does not work}

For this project, plain HTML retrieval is insufficient for five concrete reasons:

\begin{enumerate}
  \item many pages render critical controls through JavaScript after load;
  \item active stream URLs often appear only in network requests after play/click actions;
  \item iframe content can be isolated and absent from the top-level DOM snapshot;
  \item anti-bot defenses may show alternate HTML to suspicious sessions;
  \item visible state transitions (loading, paused, playing, error overlays) require
    visual confirmation.
\end{enumerate}

This is why browser-assisted extraction is not optional in this domain.

\textbf{Decision rationale.} n8n was used first because it is free, self-hostable,

at the highest complexity and cost.

platform because: n8n workflows became large and difficult to reason about as prompts
and tools evolved; parallel branches increased recovery complexity; and memory behavior

rapid-iteration lessons while giving engineering-grade control over memory, tracing, and
cost.

\section{Common break tactics and the platform's responses}

Piracy sites use a fairly consistent set of tactics to make extraction difficult. Redirect chains open ad popups before the real player appears. Nested iframes hide the actual media request several layers deep, often across different domains. Stream URLs are signed and short-lived, only generated after runtime JavaScript logic runs. Bait resources — assets with names that look like stream manifests — appear in network traffic alongside the real thing. And Cloudflare-style challenge pages serve completely different HTML when automation signals are detected.

The handling strategies are summarized in Table~\ref{tab:difficulty-handling}.

\section{Ad blocking and continuous anti-bot adaptation}

Illegal streaming sites monetize through aggressive advertising, and this creates a real problem for automation: popups open new browser contexts and divert interaction away from the actual player, while redirect chains triggered by ad clicks can leave the original page unusable. Two Chromium extensions handle most of this at the network level: uBlock Origin blocks ad server domains and injected scripts before they execute, while Ghostery covers tracker-triggered popup behavior on first page visit. Neither extension is a complete solution — sites that serve ads from the same domain as player content can't be filtered without breaking the player — so the hosting and embedded agents retain explicit popup handling logic as a fallback.

Anti-bot adaptation is not a one-time setup. Fingerprint profiles, adblock filter lists, and interaction timing all required periodic adjustment throughout the internship; the environment changes too often for a static configuration to stay reliable.

\section{Streaming protocol infrastructure}

Understanding the protocols used by streaming piracy infrastructure is a prerequisite for
understanding what the platform is designed to capture. Piracy hosts do not use a single
streaming technology: content is served over several adaptive-bitrate protocols, each with
its own manifest format, URL structure, and tokenization scheme. The \texttt{harvest} tool
is built to intercept all of them simultaneously.

\subsection{HLS — HTTP Live Streaming}

HLS~\cite{hls-rfc} is the dominant adaptive-bitrate protocol encountered in this domain.
It is text-based and organized in a strict two-level hierarchy.

The \textbf{master playlist} (commonly named \texttt{index.m3u8}, \texttt{manifest.m3u8},
or \texttt{playlist.m3u8} depending on the CDN) lists every available rendition with its
bitrate, resolution, and codec. Each rendition entry points to a \textbf{variant playlist}
that contains time-coded references to the actual MPEG-2 Transport Stream media segments
(\texttt{.ts} files). The player selects the appropriate variant based on available
bandwidth.

From an evidence perspective, the master playlist URL is the most important artifact because
it is the entry point that ties the stream to a specific CDN path. Several URL patterns
appear regularly across piracy infrastructure:

\begin{itemize}
  \item \texttt{/live/index.m3u8} — the canonical HLS master playlist;
  \item \texttt{/stream/mono.m3u8} — a single-rendition playlist that skips the master
    level; the player goes directly to segments;
  \item \texttt{/hls/playlist.m3u8?token=\textit{xxx}\&expires=\textit{timestamp}} —
    a tokenized manifest where signed query parameters grant short-lived CDN access;
  \item \texttt{/live/manifest.m3u8} — an alternative naming convention common on
    infrastructure built around open-source re-streaming panels.
\end{itemize}

Tokenized manifests are the most operationally significant variant. The token in the query
string is signed by the CDN key server and carries an expiry timestamp. The \texttt{harvest}
tool captures the full URL including the token at the moment the browser requests it,
preserving complete evidence before the token expires.

\subsection{MPEG-DASH}

MPEG-DASH (Dynamic Adaptive Streaming over HTTP, ISO/IEC 23009-1) is the second protocol
regularly encountered. Unlike HLS, DASH manifests are XML documents (\texttt{.mpd}) that
describe a hierarchical segment addressing scheme:

\begin{itemize}
  \item \textbf{MPD} (Media Presentation Description) — the root XML manifest;
  \item \textbf{Period} — a contiguous time range of the presentation;
  \item \textbf{AdaptationSet} — a group of representations sharing the same media type
    (video, audio, or subtitles);
  \item \textbf{Representation} — one specific quality level with its codec and bitrate;
  \item \textbf{SegmentTemplate} or \textbf{SegmentList} — the addressing scheme for
    individual \texttt{.m4s} fragment files.
\end{itemize}

The \texttt{harvest} tool captures DASH manifests via the URL pattern
\texttt{/\textbackslash.mpd(\textbackslash?|\$)/i}, which matches naming conventions such
as \texttt{manifest.mpd}, \texttt{stream.mpd}, and \texttt{dash.mpd}.

\subsection{Additional protocols captured}

Beyond HLS and DASH, the \texttt{harvest} tool captures three further protocol families:

\begin{itemize}
  \item \textbf{Progressive MP4} (\texttt{.mp4}) — static download links embedded in
    player configuration objects; less common on live streams but present on replay and
    clip pages.
  \item \textbf{WebM} (\texttt{.webm}) — the Chromium-native open container format, used
    on some alternative-player implementations and lower-quality fallback streams.
  \item \textbf{Smooth Streaming} (\texttt{.ism/manifest}) — the Microsoft-origin
    fragmented-MP4 format, occasionally found on infrastructure using legacy streaming
    servers.
\end{itemize}

\subsection{The harvest tool's six-layer capture strategy}

The \texttt{harvest} tool uses six parallel detection layers to ensure manifest URLs are
captured regardless of which protocol is in use and regardless of whether the manifest
loaded before the tool was invoked:

\begin{enumerate}
  \item \textbf{CDP \texttt{Network.requestWillBeSent}} — the Chrome DevTools Protocol
    fires this event for every outgoing network request, including from within cross-origin
    iframes. This is the primary layer and fires before the request leaves the browser.
  \item \textbf{Puppeteer response listener} — a secondary \texttt{page.on('response')}
    handler provides redundancy and captures response HTTP status codes alongside the URL.
  \item \textbf{DOM element scan} — the tool queries \texttt{<video src>} and
    \texttt{<source src>} attributes for statically embedded stream references.
  \item \textbf{JavaScript player API inspection} — \texttt{page.evaluate()} probes
    known player surfaces: hls.js instance URLs, video.js current source, jwplayer
    playlist items, and dash.js manifest references.
  \item \textbf{\texttt{performance.getEntriesByType('resource')}} — a retroactive
    resource-timing scan recovers manifest URLs loaded before the tool began listening.
  \item \textbf{Frame-level CDP session} — when the player is in a cross-origin iframe,
    a dedicated CDP session is opened on that frame to capture its network traffic
    independently.
\end{enumerate}

All captured URLs are matched against the protocol patterns and returned grouped by
protocol. The concrete implementation is detailed in Chapter~5.

\section{Remaining limitations of rule-based approaches}

Even with the mitigations above, difficult websites remain. This justifies the fallback
role of the agentic path:

\begin{itemize}
  \item some protections still force partial evidence outcomes;
  \item highly dynamic pages can invalidate previously successful selectors quickly;
  \item operational cost grows with deeper exploration and server count.
\end{itemize}

For this reason, the adaptive workflow is used where its flexibility provides clear
recovery value.

With the technical background established — the domain challenges, the tools selected to
address them, the streaming protocols being targeted, and the remaining limitations that
motivate adaptivity — Chapter~3 formalizes the methodology, requirements, and design
constraints that guided the system's architecture.
