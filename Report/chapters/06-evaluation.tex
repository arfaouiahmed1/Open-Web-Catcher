\chapter{Evaluation and Testing}

This chapter evaluates Open Web Catcher (OWC) as an evidence-production system for
rights-protection review. The goal is not to claim production-grade piracy detection or
universal illegal-streaming coverage. The goal is to check whether the platform can take
a suspected streaming page and produce a traceable evidence package: route decision,
agent activity, screenshots, stream evidence, provider intelligence, email readiness,
and operating-cost telemetry.

The evaluation is organized in the same order as the real review workflow. First, the
chapter defines the business question. Then it explains the batch-test design and the
status taxonomy used to interpret results. After that, it evaluates each specialist
agent, studies one concrete run in detail, and reviews the dashboard telemetry and cost
metrics. This structure is important because the final run status alone is too weak for
this project: a website can fail because an agent behaved badly, but it can also fail
because the site is dead, a hosting page is inaccessible, a stream server is down, or an
embedded player does not expose media during the capture window.

\section{Evaluation Objective and Business Context}

\subsection{Business Issue}

The practical business issue is manual uncertainty. A suspected live-sports streaming
website rarely exposes all useful evidence on the first page. A landing page may only
list matches. A hosting page may hide the player behind server buttons, popups, or
delayed activation. An embedded page may be reachable only through an iframe or after a
specific hosting server is selected. Even when a playlist URL is found, it still needs to
be connected to screenshots, provider metadata, and a notice draft before a reviewer can
use it.

In a beIN-context rights-protection workflow, the analyst therefore needs an evidence
bundle, not only a classification label. Soft Stars provides the internship engineering
context, while beIN MEDIA GROUP provides the media-rights context in which live-sports
piracy is treated as an operational protection problem.

\subsection{Evaluation Question}

The central evaluation question is:

\begin{quote}
Does OWC reduce manual uncertainty by producing a traceable, screenshot-supported, and
provider-enriched evidence package that a human reviewer can inspect?
\end{quote}

This question is more suitable than a generic accuracy score because OWC is an agentic
browser system. The reviewer needs to know what the agents did, which page state was
observed, which server path was attempted, what evidence was captured, and what remained
uncertain.

\subsection{Reviewable Evidence Bundle}

For this report, a run is considered reviewable when it can provide a meaningful subset
of the following evidence:

\begin{itemize}
  \item seed URL and persisted run identifier;
  \item page-route decision and specialist-agent handoff;
  \item landing, hosting, or embedded-player navigation evidence;
  \item player activation, server switching, iframe inspection, or documented blocker
  evidence;
  \item stream evidence such as manifest, embedded, media, or playlist URLs;
  \item screenshots that validate the page, player state, server path, or failure
  condition;
  \item provider enrichment for the stream or playlist host;
  \item abuse-contact and takedown-email draft fields when available;
  \item trace, tool-call, token, cache, latency, and cost telemetry.
\end{itemize}

\subsection{Evidence-First Evaluation}

The chapter treats metrics as support for evidence review, not as a replacement for it.
A strict success rate shows how many runs reached the strongest terminal status, but it
does not explain partial evidence, website availability, server availability, or
agent-level behavior. For this reason, the evaluation separates strict success,
productive evidence, external blockers, agent/runtime failures, repeatability, and cost.

\section{Evaluation Protocol and KPI Definitions}

\subsection{Batch Test Design}

\subsubsection{Input Set and Repeated Runs}

The batch evaluation is organized around websites. A batch contains suspected streaming
URLs with different page structures: landing pages, hosting pages, embedded players,
redirecting pages, inactive pages, and pages whose server buttons change over time. Each
URL is launched through the same pipeline: classification, specialist routing,
evidence extraction, provider enrichment, and review-output generation.

The repeated-run idea is important for this domain. A website that works once may stop
working later because a player server goes offline, a page redirects, the site changes
its anti-bot behavior, or the stream is available only during a live event. Repeated
runs therefore test not only initial success, but also whether evidence-producing sites
remain evidence-producing after prompt, tool, browser, or website changes.

\subsubsection{Manual Review After Automated Status}

After each batch run, the automated status is reviewed together with the trace,
screenshots, stream records, provider rows, and email records. This manual review step
is necessary because the same terminal status can hide different causes. For example,
a no-stream result may happen because the agent failed to activate the player, but it
may also happen because all available servers were down during the run.

A website is accepted only when the run produces evidence that can be inspected. This is
stricter than simply reaching a terminal state.

results, but they are not the same as a bad classification or an incorrect browser-tool

\subsubsection{External Blockers Are Not Automatically Agent Faults}

This distinction is especially important for live-streaming pages. A site can be down.
A match page can exist while all hosting pages have been removed. A hosting page can be
reachable while the selected server is down. An embedded player can load visually but
produce no manifest request. These cases still reduce operational yield, but the agent
evaluation should record them as availability or evidence-path blockers unless the trace
shows that the agent skipped an available action.

behavior owned by each agent instead of treating the whole workflow as one black box.

\subsection{Classification and Landing Tests}

\subsubsection{Classification Tests}

Classification is tested first because it decides the rest of the workflow. A correct
classification result should identify whether the seed page behaves like a landing page,
hosting page, embedded page, redirect, inaccessible page, or unsupported state. The
review checks the route, the confidence, the visible evidence used for the decision, and
whether the next agent receives the correct handoff.

\subsubsection{Landing Tests}

Landing-page tests check whether the agent can move beyond a listing page. The reviewer
looks for match cards, event links, watch buttons, schedule sections, pagination, and
host candidates. A landing page is not considered a failure just because it does not
contain a stream. It only becomes an agent problem if useful hosting candidates were
visible and the agent missed them. If the page genuinely exposes no usable downstream
route, \texttt{no\_hosting\_pages} is the more accurate status.

\subsection{Hosting Tests}

\subsubsection{Player Activation}

Hosting-page tests focus on interaction. The reviewer checks whether the agent clicks
the correct player controls, survives popups, returns to the player when focus is stolen,
and waits long enough for the page to generate media activity. The screenshot must be
taken after a meaningful state change, not before the player has been activated.

\subsubsection{Server Detection and Switching}

Many streaming pages expose several server choices. The hosting agent is expected to
detect server controls, try them in a reasonable order, and record which server path was
used. If server 1 is down but server 2 works, the agent should continue instead of
stopping too early. If all servers are down, the result is a server/player availability
blocker rather than automatically an agent failure.

\subsubsection{Stream Capture Order}

Stream capture is evaluated after activation and server switching. This order matters:
harvesting network traffic too early can produce empty results even when the page would
generate a playlist after a play action. A passing hosting result therefore connects the
browser action, player state, screenshot, and stream evidence in the trace.

\subsection{Embedded Tests}

\subsubsection{Iframe and Player Inspection}

Embedded-page tests check whether the agent can inspect iframe/player contexts without
mixing them with landing-page exploration. The agent should identify the embedded URL,
inspect the frame or player state, attempt playback where appropriate, and harvest media
requests after the page has had time to load.

\subsubsection{Embedded-Page Inaccessible Cases}

An embedded page can be inaccessible even when the hosting page is reachable. It can also
load visually but never expose a playlist during the capture window. The evaluation
records these as embedded availability or no-stream outcomes unless the trace shows that
the agent skipped an obvious available action.

\subsection{Provider and Email Tests}

\subsubsection{Provider Intelligence Criteria}

Provider analysis starts from concrete stream evidence. Playlist URLs are useful because
their host identifies the infrastructure that can be used for provider lookup and abuse
contact discovery. The provider test checks host extraction, DNS/IP resolution when
available, autonomous-system or organization enrichment, country fields, and whether the
result is attached to the correct run and stream record.

\subsubsection{Email Readiness Criteria}

The generated email is not treated as an automatic enforcement action. It is evaluated
as a draft. A draft is review-ready when it contains the provider/contact, infringing
page, playlist host, stream evidence, screenshot references, and a clear need for human
verification before sending.

\subsection{Agent Dashboard Evidence}

\input{figures/tikz/fig-06-dashboard-agents}

The agents dashboard supports behavior-level evaluation by separating agent runs, tool
calls, LLM calls, context tracking, and status by agent type. It helps locate where a

\subsection{Interpretation of the Current Results}

The current strict success rate is low, and that is a real limitation of the current
system. However, the raw failure rate should not be interpreted as one number meaning
``the agents failed''. The batch contains productive partials, external blockers,
cancelled runs, and true agent/runtime failures. A data-science interpretation must keep
those categories separate before comparing prompt versions, browser settings, or model
runtimes.

The most useful conclusion is therefore not that OWC has solved illegal-streaming
evidence collection. It has not. The useful conclusion is that OWC now exposes the right
evaluation objects: agent route, navigation path, server switching, screenshot timing,
stream capture, provider enrichment, email readiness, repeatability, and cost.

\section{Chapter Conclusion}

This evaluation judges OWC by agent behavior and evidence quality. The selected run is
successful because it provides a reconstructable path from a seed URL to route
classification, landing navigation, hosting/player evidence, screenshots, HLS playlist
evidence, provider enrichment, cost telemetry, and a generated email draft for human
review. The broader batch snapshot shows that the system is measurable, but also that
strict success remains low and many terminal rows require failure-category
interpretation.

For a final-year data-science project, the main evaluation contribution is the
measurement framework itself. Instead of hiding everything inside a generic accuracy
score, the report evaluates OWC through strict success, partial evidence, external
blockers, agent/runtime failures, repeatability, tool reliability, provider enrichment,
email readiness, and operating cost.
