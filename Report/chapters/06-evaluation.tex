\chapter{Evaluation and Testing}

This chapter evaluates the implemented system from three angles. First, it explains the
tests used to protect the implementation from regressions. Second, it defines the KPI
formulas used by the dashboard and by the manual evaluation. Third, it compares prompt,
model, tool, cache, and cost behavior across the main evidence-collection use cases.

The evaluation is intentionally split into dashboard-observed values and manual
reference-set values. The dashboard values come from the local observability database
used by the operator console. At the time of writing, that database contains a small
engineering snapshot, not a large production benchmark. Manual reference-set values are
therefore used to evaluate the browser-agent behavior more directly.

\section{Evaluation Sources}

Evaluation used four evidence sources:

\begin{itemize}
  \item automated regression tests for routing, prompt contracts, JSON handling, dataset

  \item dashboard metrics persisted in the local run database;

  \item prompt/tool comparison runs over representative page patterns.
\end{itemize}

\section{KPI Definitions and Formulas}

The dashboard and manual evaluation use deterministic formulas. Let $N$ be the number of
evaluated runs, $N_t$ the number of terminal runs, $S$ successes, $P$ partial successes,
$F$ failures, and $C$ cancellations.

\begin{table}[H]
\centering
\begin{tabularx}{\textwidth}{>{\raggedright\arraybackslash\bfseries}p{4.0cm}
                              >{\raggedright\arraybackslash}X}
\toprule
\rowcolor{accent!8}
Metric & Formula and interpretation \\
\midrule
Terminal runs & $N_t = S + P + F + C$. Running rows are excluded from final-quality
rates. \\
Success rate & $S / N_t$. Measures completed runs that reached a successful final
state. In the dashboard snapshot: $2/9 = 22.2\%$. \\
Failure rate & $F / N_t$. Measures terminal runs that failed. In the dashboard snapshot:
$4/9 = 44.4\%$. \\
Cancellation rate & $C / N_t$. Measures runs stopped by operator or runtime control.
In the dashboard snapshot: $3/9 = 33.3\%$. \\
Stream evidence rate & number of terminal runs with \texttt{stream\_count > 0} divided
by $N_t$. In the dashboard snapshot, this is $1/9 = 11.1\%$. \\
Page classification accuracy & correctly classified pages divided by manually verified
pages. This is evaluated by comparing the selected specialist path with reviewer labels. \\
Navigation recall & valid hosting candidates found divided by manually verified hosting
candidates available on the landing page. \\
Player activation rate & player activation successes divided by player activation
attempts. A success requires visible state change, media state change, or stream evidence. \\
Stream URL extraction rate & runs with valid \texttt{m3u8}, \texttt{mpd}, \texttt{mp4},
or equivalent embedded evidence divided by extraction attempts. \\
Tool success rate & successful tool calls divided by observed tool calls. Tool rows or
runtime events can be used as the source. \\
Cache hit ratio & cached input tokens divided by total input tokens:
$cached\_input\_tokens / (cached\_input\_tokens + new\_input\_tokens)$. \\
Cost per accepted result & total estimated cost divided by accepted evidence bundles.
This is only meaningful when LLM cost telemetry is persisted. \\
\bottomrule
\end{tabularx}
\caption{KPI formulas used by the dashboard and the manual evaluation.}
\label{tab:kpi-formulas}
\end{table}

\section{Cost Estimation Formula}

Cost is estimated from token usage and model pricing. The implementation records
separate cost components so that cached tokens are not treated like normal input tokens.
For a model with prices expressed per million tokens, the estimated cost is:

\[
\begin{array}{rl}
Cost = & \frac{new\_input\_tokens}{1{,}000{,}000} \times input\_price \\[0.4em]
& + \frac{cached\_input\_tokens}{1{,}000{,}000} \times cached\_input\_price \\[0.4em]
& + \frac{cache\_write\_tokens}{1{,}000{,}000} \times cache\_write\_price \\[0.4em]
& + \frac{output\_tokens}{1{,}000{,}000} \times output\_price
\end{array}
\]

The dashboard exposes the same split as input cost, cached-input cost, cache-write cost,
output cost, and total cost. When provider-reported cost is available, it can be used
directly. Otherwise, the system resolves model pricing from the configured provider
pricing catalog and calculates the estimate from recorded usage metadata.

The main regression lesson is that lower tool-call count is not automatically better.
The v1 prompt was cheaper because it stopped too early. The ReAct prompt increased tool

without removing necessary verification.

\section{Cache and Pricing Evaluation}

Caching was evaluated as an operational control. It reduces repeated context cost when
large stable prompt sections, tool descriptions, and repeated page observations are
reused. The key formulas are:

\[
CacheHitRatio = \frac{cached\_input\_tokens}{cached\_input\_tokens + new\_input\_tokens}
\]

\[
TokensPerAcceptedEvidence = \frac{input\_tokens + output\_tokens}{accepted\_evidence\_bundles}
\]

\[
CostPerAcceptedEvidence = \frac{total\_estimated\_cost}{accepted\_evidence\_bundles}
\]

In the current dashboard snapshot, cached tokens, new tokens, and total cost are all
zero because no model telemetry rows were persisted. During heavier manual campaigns,
the observed pattern was approximately 800k total context tokens with about 690k served
from cache, corresponding to roughly 80\% or more cache reuse depending on which run
phase is included in the denominator.

\section{Chapter Conclusion}

The evaluation shows that the system should be judged as an evidence-collection workflow,
not as a single classifier. Page classification matters, but successful evidence
collection also depends on navigation, player activation, server switching, popup
handling, redirect recovery, stream extraction, metadata enrichment, screenshot
reasoning, trace support, cost visibility, and cache behavior.

The dashboard snapshot proves that the observability pipeline can summarize run status,
stream counts, duration, and cost fields, but the current local data is too small and too
synthetic for final accuracy claims. The manual reference set gives the stronger signal:
moving from intent-based prompts to ReAct-style prompts, then adding popup handling,
media-state verification, and budget-aware early exit, substantially improved navigation,
player activation, and tokenized-stream recovery.

The main engineering lesson is that evaluation must remain regression-oriented. Every
new prompt, tool, model, or browser policy should be tested against the same use cases so
that improvements in one area do not break another.
