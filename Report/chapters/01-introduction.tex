\chapter{Introduction}

\section{Host organization — Soft Stars}

Soft Stars is a software company specializing in digital media intelligence and content
protection solutions. The company develops technical platforms for monitoring, detecting,
and documenting unauthorized redistribution of premium audiovisual content across global
streaming piracy networks. Its engineering work spans automated browser workflows, web
intelligence, data enrichment pipelines, and rights-enforcement tooling built to the
operational requirements of major media rights holders.

This internship was conducted within Soft Stars for the client \textbf{beIN SPORTS}, one
of the world's largest sports broadcasting networks. The official project title was
\textit{Design of a Multi-Agent AI Pipeline for Evidence Collection from Illegal Streaming
Sites}. The mission was to design, build, and evaluate a platform capable of visiting
suspicious target websites, understanding their page structure, extracting stream evidence,
and producing structured, auditable outputs that support legal and operational
enforcement action.

\section{Sports piracy and the evidence collection challenge}

The broadcasting rights market for premium football and sports content represents an
industry worth tens of billions of dollars globally. Rights holders such as beIN SPORTS
invest heavily in acquiring exclusive licences that entitle them to distribute specific
events to specific territories. Illegal streaming sites undermine those rights by
redistributing protected content without authorisation, often at no cost to the viewer.
The scale of the problem is significant: hundreds of aggregator domains may broadcast
the same protected match simultaneously during a major competition
window~\cite{muso-piracy,audiovisual-obs}.

From an enforcement perspective, the first obstacle is \textit{evidence}. Before a
rights holder can act legally or operationally, it needs to prove:

\begin{itemize}
  \item that a specific URL was accessible during a specific broadcast window;
  \item that the page delivered a live or on-demand stream of protected content;
  \item that the stream was hosted or relayed through identifiable infrastructure;
  \item that the stream resolved to a playable URL (typically an HLS \texttt{.m3u8}
    manifest or MPEG-DASH \texttt{.mpd} file).
\end{itemize}

Producing that proof at scale is an engineering problem. Manual monitoring cannot cover
hundreds of domains simultaneously. A static HTML scraper cannot handle pages that require
JavaScript execution, user interaction, or network-level observation to reach the stream
URL. A rule-based system tied to fixed CSS selectors breaks every time a site operator
updates their template. The internship project addresses this gap: how to collect the
necessary evidence automatically, at scale, and traceably across a heterogeneous and
continuously changing population of streaming sites.

\section{Why the problem requires an adaptive approach}

Three structural properties of illegal streaming sites make them resistant to conventional
automation.

\paragraph{Structural heterogeneity.}
The target population includes sites built on dozens of different technology stacks:
WordPress-derived templates shared across Arabic-language site families, custom React or
Vue frontends on global hubs, PHP-driven backends with client-side overlay logic, and
fully bespoke single-page applications. No single selector or fixed crawl path works
across all of them.

\paragraph{Deliberate obfuscation.}
Site operators are incentivised to make automation difficult. Common countermeasures
include Cloudflare bot-challenge pages, JavaScript-injected play buttons that do not
exist in the initial HTML, advertising overlays that must be dismissed before the player
is accessible, tokenized stream URLs that expire within seconds and require player
activation before the manifest is generated, and nested iframe trees that distribute the
player across two or three origin domains.

\paragraph{Continuous change.}
Domains rotate frequently. Layouts are updated between broadcast windows. Anti-bot
configurations are adjusted in response to detection. Effective evidence collection
therefore requires not just a working solution but a \textit{maintainable} one where the
adaptation cost per site family is minimized.

These three properties together motivate the use of AI agents. An agent equipped with
browser tools, a structured reasoning prompt, and persistent memory of past observations
can adapt its extraction strategy at runtime in response to what it actually finds on the
page.

\section{Project evolution: from prototype to platform}

The project did not start with the final coded platform. The first phase used \textbf{n8n}
as the main experimentation environment. This allowed rapid assembly of browser action
sequences, early prompt testing on real targets, and end-to-end workflow validation with
minimal development overhead. The n8n phase confirmed that the multi-agent extraction
approach was viable and surfaced the operational realities of the target domain.

As the scope matured, the need for stronger observability, finer control over runtime
behavior, explicit cost optimization, and a maintainable prompt and tool evolution cycle
made it clear that a coded platform was required. The project transitioned to a solution
built with \textbf{FastAPI}, \textbf{Next.js}, \textbf{Puppeteer}, structured persistence,
and dedicated evaluation tooling. This transition preserved all the extraction logic
validated in the prototype while adding engineering maturity: persistent memory,
per-run cost tracking, streaming observability, and a containerized deployment model.

\section{Problem statement}

The main problem addressed by this internship can be stated as:

\begin{quote}
How can we design a maintainable and extensible multi-agent platform that analyses
illegal streaming websites, distinguishes different page roles, extracts evidence-grade
stream and infrastructure data, and remains effective despite dynamic interfaces,
multilingual layouts, anti-bot barriers, and continuously evolving site behavior?
\end{quote}

This problem is difficult for several reasons:

\begin{itemize}
  \item a single website can expose landing pages, hosting pages, embedded players,
    and auxiliary pages in the same session;
  \item the evidence (stream URLs, screenshots, iframe chains) may appear only after
    clicks, navigation, or player activation;
  \item page structure changes frequently, making brittle hard-coded rules obsolete
    quickly;
  \item LLM inference cost grows fast if agent context and tool allocation are not
    controlled carefully.
\end{itemize}

\section{Objectives and contributions}

The main objective was to design and implement a multi-agent pipeline capable of
processing suspicious streaming websites end to end. This breaks down into the following
operational goals:

\begin{itemize}
  \item classify each input URL before deeper extraction begins;
  \item route the URL toward specialized agents according to page type;
  \item collect hosting links, embedded links, and stream URLs through browser-assisted
    adaptive extraction;
  \item preserve screenshots, tool-call traces, and final results for auditable review;
  \item analyze the infrastructure behind extracted streams;
  \item support takedown preparation with structured evidence output;
  \item expose the system through an operational interface and a programmatic API;
  \item prepare the solution for containerized event-driven deployment on Azure.
\end{itemize}

The internship produced contributions at both prototype and platform level:

\begin{itemize}
  \item \textbf{n8n prototype}: rapid validation of the extraction pipeline and early
    prompt experimentation on real target websites;
  \item \textbf{Four-agent architecture}: specialist agents for classification,
    landing-page discovery, hosting extraction, and embedded-player analysis,
    each with a targeted ReAct-style prompt and dedicated tool allocation;
  \item \textbf{Browser tool layer}: six Puppeteer-based tools (inspect, interact,
    harvest, screenshot, navigate, get\_media\_state) enabling adaptive page interaction
    beyond static HTML retrieval;
  \item \textbf{Operator platform}: FastAPI backend with structured observability plus
    a Next.js operator console for live run streaming, history, and evaluation review;
  \item \textbf{Memory and caching}: short-term run-level memory and long-term site
    memory profiles, combined with provider-side prompt caching to control inference cost.
\end{itemize}
