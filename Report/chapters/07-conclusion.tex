\chapter{Conclusion and Perspectives}

\section{General Conclusion}

This internship produced an agentic evidence-collection system for illegal sports
streaming websites. The work started from a practical problem: streaming-piracy pages do
not expose evidence through simple static HTML. They use dynamic listings, JavaScript
tabs, popup traps, nested iframes, click-gated players, redirects, provider checks, and
short-lived stream URLs. The final system therefore had to behave more like a controlled
browser investigator than a normal scraper.

The project followed a general-to-specific progression. The n8n phase validated the core
idea quickly: an LLM-guided browser workflow can inspect pages, follow page transitions,
activate players, and recover evidence. The Python reference implementation then turned
that prototype into a more maintainable architecture with FastAPI, a Next.js operator
console, profiled MCP browser tools, specialist agents, memory and cache support,
PostgreSQL/SQLite observability, and cost-aware model telemetry.

The most important result is not a single extraction trick. It is a repeatable
engineering framework for investigating unstable websites while preserving reviewable
evidence: traces, screenshots, stream candidates, page classifications, model/tool
usage, and failure reasons.

\section{Technical Lessons}

\subsection{Prompt structure matters}

The largest reliability gain came from replacing broad intent-based prompts with
ReAct-style prompts. The agent needed to observe, state a hypothesis, choose one action,
verify the result, and then continue or stop. Without that loop, the system stopped too
early, missed hidden tabs, harvested before activation, or accepted weak evidence.

\subsection{Browser evidence must be layered}

DOM text alone was not enough. A valid result needed several evidence layers: visible
state, screenshot context, tool trace, media state, stream URL, iframe path, and final
structured output. This is why the implementation treats screenshots and runtime events
as core evidence rather than debugging extras.

\subsection{Fallbacks are part of the architecture}

Streaming websites rarely follow one clean path. Landing pages may link to host pages,
host pages may redirect to embedded players, and embedded players may be nested several
frames deep. The hosting-to-embedded fallback was therefore essential. It allowed the
system to recover cases that a single-stage scraper would mark as failed.

\subsection{Evaluation must be regression-oriented}

The evaluation showed that every improvement can create a new failure. More tool calls
can improve recovery, but also increase cost. More aggressive ad blocking can reduce
noise, but can also break a player. A stronger prompt can improve one page type while
overfitting another. The correct evaluation method is therefore regression testing across
stable use cases: classification, landing navigation, player activation, server
switching, popup handling, redirect handling, stream extraction, and metadata enrichment.

\section{Limitations}

The system remains a reference architecture, not a finished production enforcement
platform. The main limitations are:

\begin{itemize}
  \item anti-bot and provider behavior changes continuously;
  \item some runs still require human review before the evidence can be trusted;
  \item the local dashboard snapshot is small and does not yet represent production-scale
    accuracy;
  \item model and pricing telemetry must be collected over more real runs before a true
    LLM model leaderboard can be claimed;
  \item deeply nested iframe chains, token expiry, and popup-heavy pages still require
    careful budget and retry policies.
\end{itemize}

These limitations do not invalidate the approach. They define the next engineering
steps: larger evaluation sets, more stable telemetry capture, clearer model comparisons,
and stronger run-level validation.

\section{Future Work}

The most useful short-term improvements are practical:

\begin{itemize}
  \item expand the fixed benchmark set with labeled landing, hosting, embedded, popup,
    redirect, and tokenized-stream cases;
  \item persist model/tool telemetry consistently for every dashboard run so cost,
    cache, and model comparisons are always available;
  \item add automated regression suites for each agent and each page behavior;
  \item improve candidate ranking so the system spends less time on low-quality host
    pages and dead server buttons;
  \item refine memory so successful selectors, server labels, and provider patterns can
    be reused without hardcoding websites;
  \item move long browser work to queue-driven workers while keeping the operator console
    responsive.
\end{itemize}

\subsection{Screenshot annotation layer}

A useful operator-console extension is a canvas-based screenshot annotation layer. The
system already captures screenshots; the next step is to let reviewers mark evidence
regions directly: server buttons, play controls, iframe containers, blocking overlays,
broadcaster logos, player state, and stream-relevant UI areas.

Each annotation can be stored as structured metadata linked to the run, screenshot URL,
page URL, timestamp, and reviewer. This would improve human review, make report figures
clearer, and support evidence handoff without modifying the target website.

\section{Final Remarks}

The project demonstrates that agentic browser automation is a suitable approach for this
domain when it is constrained, observable, and evaluated carefully. The final value is
not that the system permanently defeats every anti-bot technique. The value is that it
turns a messy investigation process into a structured workflow: classify the page,
navigate deliberately, activate and verify the player, extract evidence, preserve the
trace, estimate the cost, and learn from failures.

That framework gives Soft Stars a foundation for continuing the work: more data, more
evaluation, more robust deployment, and clearer operational review.
